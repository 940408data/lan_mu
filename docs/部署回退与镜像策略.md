# 部署回退与镜像策略

> 2026-08-14 首次制定。记录本地镜像现状、回退陷阱与方案、回退脚本用法。
> 配套脚本 `tools/rollback.sh`。

## 一、部署现状（2026-08-14 实测）

### 本地镜像

- **仅 1 个**：`lan-mu:latest`（48MB 内容 / 149MB 含 `nginx:alpine` 基础层）。
- **无历史版本**：`dangling` 为空。每次 `docker compose build` 覆盖 `latest` 标签，旧镜像不保留——**本地无旧镜像可直接回退**。
- **无 registry 凭证**：未登录任何 registry（docker hub / ghcr 等）。

### 架构关键点：镜像非自包含

- `docker-compose.yml` 把 `./dist:/media:ro` 挂载：**重媒体（jpg/png/pdf）走 volume，不在镜像内**。
- `Dockerfile` `COPY dist/`：仅轻量部分（HTML/CSS/字体 woff2）入镜像；`.dockerignore` 排除 `dist/**/*.{pdf,png,jpg,jpeg}`。
- 镜像瘦身约 25 倍（见 `infra/docker-media-mount`），代价是镜像不含重媒体。

### 部署各阶段实测时长

| 阶段 | 耗时 | 说明 |
|---|---|---|
| `git push origin dev` | 4s | |
| 重建站点页（`node tools/gen-index.js`） | 3s | dist 过时只波及站点页时，单跑 gen-index 替代全量 build |
| `docker compose build` | 5s | `nginx:alpine` + `nginx.conf` 缓存命中，仅 `COPY dist/` 重跑 |
| `docker compose up -d` | 1s | 容器 Recreated → Started |
| `/healthz` 就绪 | 0s | nginx 启动即就绪 |
| **合计** | **13s** | |

> 重建极快的前提：**dist 过时部分仅限站点页**（改动只动 `src/site/`，未触及 `works/` 与 `src/core/`），单跑 `gen-index`（3s）即可，无需全量 `npm run build`。若 `works/` 或 `src/core/` 有改动，须全量 build（Playwright 出图 + 宋版每字面 PDF，约 15-30min）。

## 二、风险与回退陷阱

### 陷阱：镜像层面回退不完整

镜像不含重媒体。**用旧镜像回退时，宿主 `dist/` 仍是新版 → 旧镜像的 HTML 引用新图可能 404 或错配**。回退必须**镜像 + dist 双版本同步**，单回退镜像不够。

> 实例：本次部署（08-14）`docker compose build` 已覆盖旧 `latest`，旧镜像（含「儒釋道」旧站点页）已不存在，本地无法 `docker run` 旧镜像回退，只能 `git checkout 0a13d25` 重建。

### 真正软肋：重媒体未版本化、未异地备份

- 镜像可从 git 任意 commit **确定性重建**（Dockerfile 简单 + dist 由 `text.yaml` + `seed` 决定），代码已在 GitHub 异地备份。
- 重媒体是 `npm run build` 的 Playwright 出图产物（全量 ~15-30min），**宿主机故障时只能从 git 全量重建恢复**。这是当前容灾的主要软肋。

## 三、回退方案

### 方案 A：本地 prev 镜像（秒级单步）

```bash
./tools/rollback.sh snapshot   # 部署前：保留当前 latest 为 prev
./tools/rollback.sh prev       # 回退：用 prev 镜像重启
```

- 速度：秒级（`docker tag` + `up -d`）。
- 局限：**仅回退镜像内 HTML/CSS/字体，dist 不变**。仅适合「镜像构建出问题/小步回退」，且 dist 与 prev 镜像同版本时安全。跨版本回退用方案 B。

### 方案 B：git tag + 重建（分钟级，完整）

```bash
git tag deploy-YYYY-MM-DD                # 里程碑部署打 tag
./tools/rollback.sh tag deploy-YYYY-MM-DD # 完整回退
```

- 完整同步镜像 + dist（`git checkout <tag>` → `gen-index` → `docker build` → `up`）。
- works 未变时 ~10s（gen-index + docker）；works 变动时全量 build 15-30min。

## 四、回退脚本

见 `tools/rollback.sh`，三模式：

| 命令 | 作用 |
|---|---|
| `snapshot` | 部署前保留当前 `lan-mu:latest` 为 `lan-mu:prev` |
| `prev` | 秒级回退到 `lan-mu:prev`（仅镜像，dist 不变） |
| `tag <git-tag>` | 完整回退：`checkout tag` → `gen-index` → `docker build` → `up`，完后切回原分支 |

## 五、建议（中期 / 远期）

- **ghcr.io + GitHub Actions**（推荐，非 docker hub）：仓库在 GitHub（`940408data/lan_mu`），ghcr 集成更好；`Dockerfile.full` 已是多阶段 CI 构建层，可让 Actions 在 push dev 时自动构建并按 commit sha 打 tag 推 ghcr。回退 = `docker pull ghcr.io/.../lan-mu:<sha>`。解决镜像异地备份 + 任意版本秒级 pull 回退（仍不含重媒体）。
- **重媒体对象存储版本化**：dist 重媒体推 S3/OSS 版本化、nginx 反代读取，把重媒体也纳入异地备份——完整容灾的最后一环。
- **当前阶段足够**：git tag + 本地 prev 覆盖回退基本盘；镜像可确定性重建，不急推远程。

## 六、部署前约定

- 每次部署前：`./tools/rollback.sh snapshot`（保留 prev，秒级单步回退备用）。
- 里程碑部署：`git tag deploy-YYYY-MM-DD`（完整回退锚点）。
- 跨版本回退：务必用 `tag` 模式同步重建 dist，勿单用 `prev`（镜像不含重媒体，详见第二节陷阱）。
