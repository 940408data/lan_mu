# 兰木项目：复杂度、开发工时与生产上线评估

> 评估时间：2026-08-11
> 评估基线：dev @ 1653bc6（宋版善刻引擎 + 手卷引擎，14 部作品，其中《論語集注》卷一至卷八数据已入库）
> 规模基准：引擎+工具链约 3100 行（src + tools，28 文件）；作品数据 text.yaml 合计约 2600 行

## 一、复杂度评价：代码量小，但复杂度密度极高

规模上它很小——引擎+工具链约 3100 行，14 部作品数据约 2600 行 YAML。但这属于「冰山型」项目，真正的复杂度藏在四个非典型维度：

| 维度 | 复杂度 | 说明 |
|---|---|---|
| **学术校录** | ★★★★★ | 最大成本项。分章依朱子本、异体字规范（閒/間/欲/云）、校勘脚注处理、底本与对校本互校——这是文献学工作，不是编程 |
| **版面引擎** | ★★★★☆ | 宋刻本式样的数字重建：半叶八行/行十六字/双行小注二十五字、版心鱼尾、朱笔圈点四式、注文三版切换。CSS 竖排双行分栏是公认难题 |
| **字体管线** | ★★★☆☆ | 三级授权（A 子集内嵌 / B 本机注入 / C 禁用）+ 子集化 + 缺字回退，设计成熟 |
| **确定性渲染** | ★★★☆☆ | seed 确定生成、expect 基准校验、逐字符比对（verify-replica），保证「一次校录」可复现 |

**结论**：这不是一个前端项目，而是一个「数字文献学工具 + 静态出版系统」，其难度结构接近排版引擎（LaTeX 那类问题的垂直缩小版），而不是常规 Web 应用。

### 架构定位补充

- **运行期**：纯静态前端（HTML/CSS/JS + 字体子集 + PDF），零依赖，可直投 nginx / GitHub Pages / 对象存储
- **构建期**：Node 工具链（排版引擎调度、字体子集、Playwright 出 PDF、opencc 繁简映射），离线生成、跑完即退
- **唯一「服务器」成分**：本地开发预览 `tools/serve.js` 与生产 nginx，均为纯静态文件服务
- 语言选型结论：构建期用 Node 与「渲染目标是浏览器」高度同构，Python 不会明显更好（渲染核心仍是 Chromium，换语言等于重写占 20% 的胶水层而 80% 的渲染核心纹丝不动）；未来若需文本分析类能力，宜采用「Python 预处理 → YAML → Node 构建」的混合架构

## 二、一般开发需要多长时间

按常规人力（不含 AI 加速）估算：

| 阶段 | 1 名熟练全栈 + 懂文献 | 2–3 人小团队 |
|---|---|---|
| 双引擎 + 字体管线 + 渲染管线 MVP | 2–3 个月 | 1–1.5 个月 |
| 手卷 4 部作品（含书法笔墨模拟） | +1–2 个月 | +3 周 |
| 宋版 14 部作品校录（工具成熟后约 1–3 天/卷） | +2–4 个月 | +1–2 个月 |
| 部署 / 打磨 | 2 周 | 1 周 |
| **合计** | **6–10 个月** | **3–4 个月** |

注意两点：

1. **校录是长尾成本**——代码一次投入，数据随卷数线性增长
2. 本项目实际在 AI 协作下数日内完成多卷推进，该速度不代表常规人力；复用其工具链（`tools/extract-lunyu.js`、`proofread*.js` 与 `songke-lunyu-volume` skill）是提速关键

## 三、生产上线可能性

**已具备**：静态零依赖运行期、Docker/nginx 部署、字体授权隔离（B 级不进 dist）、完整的查看器交互（繁简/朱点/版式/字面/披览模式）、每字面一版 PDF 分发、数据可复现。

**作为展示型站点（小流量发布、文化交流场景），今天就够格。**

正式公开运营的差距清单（按优先级）：

### 1. 内容质量兜底（最高优先级）

经典文本公开传播，一个错字就是事故。目前 8/20 卷，且校录依赖单人/AI。需要：

- 双人校对流程
- 已发布卷的勘误渠道（页面内报错入口）
- 发布前 checklist（validate 通过 + expect 基准 + 分章数核对）

### 2. 字体合规确认

英雄行楷为 B 级授权，公网分发前需书面确认授权范围是否覆盖公开托管。当前架构只在本机预览注入、dist 不泄漏，设计正确，但授权条款需书面落实。

### 3. CI/CD 缺失

构建全在本机手工。补 GitHub Actions：PR 触发 validate → build → 产物归档；否则换机器/多人协作即失控。

### 4. 可复现性隐患

B 级字体依赖本机文件，不同机器重建的行楷版 PDF 不一致。生产应锁定「构建环境唯一」或固化产物入库。

### 5. 体积与体验

单卷 PDF 30–45MB，移动端下载体验差。可做：按叶分册 PDF、首页卷次导航、移动端适配验证。

### 6. 测试空白

引擎无单测，靠 expect 基准。排版引擎（分栏/分卷/句读）应拆出可测单元，为卷九～二十铺路。

### 7. 运维基线

nginx 安全头、HTTPS、轻量访问统计、数据源备份（input_data 已入库 ✓）。

## 四、结论

- **复杂度**：代码小而密度高，本质是「文献学 + 排版引擎」，远超普通前端项目
- **工时**：常规人力 3–10 个月量级，校录是持续长尾
- **上线**：展示级上线已具备条件；若目标是正式公开运营，先补三件事即可达到及格线——**校对流程与勘误渠道、字体授权书面确认、CI 自动化构建**，其余（测试、移动端、分册 PDF）可迭代推进
